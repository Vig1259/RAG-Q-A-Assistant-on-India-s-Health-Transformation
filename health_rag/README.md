# India's Health Transformation — RAG Q&A

A small end-to-end Retrieval-Augmented-Generation (RAG) system that answers
questions about a single source document: the PIB backgrounder
**["India's Health Transformation"](https://www.pib.gov.in/PressReleasePage.aspx?PRID=2269699&reg=48&lang=2)**.

It only ever answers from this document — no other sources are ingested.

```
Question --> embed --> cosine-similarity search over chunk embeddings
   --> top-k chunks --> prompt with question + chunks --> LLM (or extractive
   fallback) --> short grounded answer + which chunks were used
```

## 1. How the document was ingested and chunked

- **Ingestion** (`ingest.py`): the PIB page is fetched over HTTP and parsed
  with BeautifulSoup, keeping headings and paragraphs and dropping images,
  scripts, the giant outbound "References" link list, and the Hindi footer.
  Bold section headers (e.g. "Pillar 1: Public Health Insurance Through
  AB‑PMJAY", "Pillar 3: Pandemic Preparedness Through PM‑ABHIM") are turned
  into `## Heading` markers so the chunker can split on them.
  If there's no network access (or `requests`/`bs4` aren't installed), ingestion
  automatically falls back to a pre-fetched, cleaned copy already checked in
  at `data/raw/pib_health_transformation.md`, so the whole pipeline always
  runs end-to-end even offline.
- **Chunking** (`chunker.py`): the cleaned text is split at `## Heading`
  boundaries — these already correspond to the natural topical sections of
  the backgrounder (AB‑PMJAY, Ayushman Arogya Mandirs, PM‑ABHIM, ABDM, NHM
  maternal/child programmes, TB/malaria/NCD elimination, AI in healthcare,
  AYUSH, etc.). Sections longer than 500 words are further split at
  paragraph boundaries (never mid-sentence) into ~350-word pieces; sections
  shorter than 200 words are merged into an adjacent section as long as the
  merge doesn't push the chunk over 500 words. Each chunk keeps a
  human-readable title, e.g. `"Pillar 3: Pandemic Preparedness Through
  PM-ABHIM"`. Run `python -m health_rag.chunker` to see the resulting 15-16
  chunks and their word counts.

## 2. Where embeddings are stored and how semantic search works

Embeddings are computed with a **pluggable backend** (`embeddings.py`),
selected via the `EMBEDDING_BACKEND` env var:

| Backend | What it is | Setup |
|---|---|---|
| `tfidf` (default) | Scikit-learn TF-IDF vectors (1-2 grams) | Nothing to install beyond `requirements.txt` — runs fully offline |
| `sbert` | Dense sentence embeddings, `all-MiniLM-L6-v2` (Sentence-Transformers) | `pip install sentence-transformers` (downloads the model once) |

Both backends implement the same `fit()/transform()` interface and produce
L2-normalized vectors, so **cosine similarity = dot product** everywhere in
the code.

`vector_store.py` builds the index once and persists it to
`data/index/`:
- `chunks.json` — chunk id, title, text, word count
- `embeddings.npy` — the (n_chunks × dim) embedding matrix
- `embedder.pkl` — the fitted TF-IDF vectorizer (or the sbert model name)
- `meta.json` — which backend was used, chunk count

On a query, the question is embedded with the *same* fitted embedder, and
`VectorStore.search()` returns the top‑k chunks ranked by cosine similarity
(`matrix @ query_vector`, since everything is unit-normalized).

## 3. How semantic search + RAG works end-to-end

1. `rag.answer_question(question)` calls `store.search(question, top_k=4)`
   to retrieve the most relevant chunks.
2. `build_prompt()` constructs a prompt that contains **only** the
   retrieved chunks as context, each labeled with its section title, plus a
   system instruction that explicitly forbids answering beyond the given
   context and requires the model to say so if the context doesn't cover
   the question.
3. The answer is generated by whichever backend is configured, tried in
   this order:
   - **Anthropic API** if `ANTHROPIC_API_KEY` is set (`claude-sonnet-4-5`
     by default, override with `ANTHROPIC_MODEL`)
   - **OpenAI API** if `OPENAI_API_KEY` is set (`gpt-4o-mini` by default,
     override with `OPENAI_MODEL`)
   - **Groq API** if `GROQ_API_KEY` is set (`llama-3.3-70b-versatile` by default,
     override with `GROQ_MODEL`)
   - **Groq API** if `GEMINI_API_KEY` is set (`gemini-2.0-flash` by default,
     override with `GEMINI_MODEL`)
   - **Extractive fallback** (always available, no key required): ranks
     sentences from the retrieved chunks by lexical overlap with the
     question and returns the top few **verbatim**. This guarantees zero
     hallucination even with no LLM configured at all, and is what the demo
     runs with by default.
4. The CLI/UI prints the answer plus the source chunk titles, a short
   snippet, and the similarity score for each, so the user can verify
   grounding.

## Setup & run instructions

```bash
# 1. Install dependencies
pip install -r requirements.txt

# 2. (Optional) Refresh the local cache by fetching the live PIB page
python -m health_rag.ingest

# 3. Build the chunk + embedding index (auto-built on first query if skipped)
python -m health_rag.vector_store

# 4a. Ask questions via CLI
python run.py "What is AB-PMJAY and how much coverage does it provide?"
python run.py                     # interactive loop, type 'exit' to quit

# 4b. Or use the minimal Flask web UI
python -m health_rag.app          # open http://localhost:5000

# 4c. Or use the Streamlit UI (chat-style, with a sidebar showing index/backend status)
streamlit run health_rag/streamlit_app.py   # opens automatically at http://localhost:8501
```

### Optional: real semantic embeddings + LLM-generated answers

```bash
pip install sentence-transformers anthropic
export EMBEDDING_BACKEND=sbert
export ANTHROPIC_API_KEY=sk-ant-...
rm -rf data/index          # force a rebuild with the new embedder
python run.py "How has TB incidence changed in India?"
```
